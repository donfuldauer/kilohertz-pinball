READ-ONLY CONTEXT
  docs/TELEMETRY_PROTOCOL.md (UDP telemetry v1: header, entries, kinds, receiver rules, full-state
  cadence, haptic source ids) — normative. pin_audio::telemetry (the sender, for producing fixtures in
  Rust). PLAN Appendix A.1 `[dof]` example (docs/PLAN.md around line 941) and Appendix B.
  DirectOutput Framework facts: DOF is a .NET library a host loads (DirectOutput.dll); the host
  initialises a `DirectOutput.Pinball` object with the table name/ROM name and pushes table-element
  updates as (type char, number, value) — e.g. `ReceiveData(char tableElementTypeChar, int number,
  int value)`. It is not available in CI: load it at runtime by reflection from the user's DOF install
  path (configurable; default from the registry/known paths) behind an `IDofSink` interface, so tests
  use a mock sink. Mark the real-DOF path "unverified on hardware" (D33).

GOAL
  A Windows-only companion process that listens to the engine's UDP telemetry, translates every
  state change of mapped coils, switches, lamps and GI strings into DOF table-element updates, and is
  started/stopped by the engine with table load when `[dof]` is present.

DELIVERABLES (PLAN 3.5)
  1. `[dof]` section in `table.toml`: the ROM-style table name DOF configs key on, and a map from engine
     coils, lamps and switches to DOF table-element type and number. (Schema exists; add load-time
     cross-reference validation and the resolved id→element map the engine hands to the bridge.)
  2. Bridge process: listens to the UDP telemetry stream, hosts the user's installed DOF, and forwards
     each change as a (type, number, value) table-element update.
  3. Engine starts and stops the bridge with table load on Windows when `[dof]` is present; a no-op on
     Linux and macOS. `pin_app::dof` provides the launcher API (spawn with args: UDP port, ROM name,
     a resolved mapping file or argument; stop/kill on unload and on drop; never blocks the sim or
     render thread); calling it from table load is 6.0's wiring — expose the API, do not edit the
     orchestrator.

DESIGN NOTES
  * Telemetry carries numeric ids; the engine resolves names → ids at table load and passes the
    resolved map (e.g. a small JSON/TOML file in a temp dir or command-line args — log the choice).
  * Value mapping: switches/coils 0/1 → 0/1; lamps and GI intensities (0..1) → 0..255; only changes are
    forwarded (full-state datagrams must not re-send unchanged values, but a first full state after
    (re)start sends everything). Handle packet loss, reordering and sender restarts per
    TELEMETRY_PROTOCOL.md receiver rules.
  * Rust side builds on all three OSes (no Windows-only deps in the default build; cfg(windows) for
    process launch specifics is fine).

VERIFICATION CRITERIA (PLAN 3.5)
  Windows CI replays recorded telemetry into the bridge with a mock DOF sink and asserts the exact update
  sequence, forwarded within 2 ms of packet arrival (measured inside the bridge from receive timestamp
  to sink call — a non-wall-clock-flaky assertion: use the bridge's own monotonic stamps and assert the
  p100 over the fixture). Builds on other platforms are unaffected. The .NET tests also run on Linux
  here (dotnet 8 is installed) so local gates can run them; CI runs them on windows-latest.
  Fixtures: recorded telemetry (binary datagrams) generated by a Rust test/helper using
  pin_audio::telemetry, checked in under tools/dof_bridge/tests/fixtures/.
  Gate 5: the bridge's datagram parser survives a bounded random-bytes run without throwing
  (FsCheck or a seeded loop).
  Coverage: pin_app ≥ 60 % (dof/ module measured); .NET line coverage reported (coverlet) — target 85 %.
